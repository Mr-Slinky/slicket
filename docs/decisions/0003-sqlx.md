# Access PostgreSQL through sqlx

## Context and Problem Statement

Slicket stores its data in PostgreSQL, as [ADR 0002](0002-postgres.md) records. The
`slicket-store` crate saves the components of `slicket-core` to the database and loads them back,
and it needs a Rust library to do so.

The backend is a hybrid Entity Component System, as [ADR 0001](0001-hybrid-ecs.md) records. A
ticket is an entity made of components, such as `TicketCore` and `ClosedAt`, in place of one
struct with a field for every piece of data. The library has to let `slicket-store` map those
components onto tables in whatever shape the schema needs.

## Decision Drivers

* Control over the SQL. The developer writes each query, so the mapping from components to tables
  stays in the developer's hands.
* Compile-time checks. The compiler catches a misspelt column or a wrong parameter type before the
  code runs.
* Async calls, so one thread serves many requests while they wait on the database.
* A complete toolset: a connection pool and migrations along with the driver.
* Code that a developer still learning Rust can read, and compiler errors that point at the fault.

## Considered Options

* sqlx
* Diesel
* SeaORM
* tokio-postgres

## Decision Outcome

Chosen option: "sqlx", because it runs SQL that the developer writes and checks that SQL at compile
time.

The `query!` and `query_as!` macros connect to the database in `DATABASE_URL` while the crate
compiles. PostgreSQL checks each query and reports the type of every column and parameter. The
macro then generates code with those types, so a nullable column arrives as an `Option`. A query
that refers to a missing column fails to compile.

sqlx also provides a connection pool, `PgPool`, and runs the migrations in
`crates/slicket-store/migrations`.

### Consequences

* Good, because the developer writes every query, so the schema can take whatever shape suits the
  components.
* Good, because a mistake in a fixed query is a compile error.
* Good, because the pool and the migrations come from one library.
* Bad, because compiling a query macro needs a running database, or the query data that
  `cargo sqlx prepare` saves to the `.sqlx` folder. A build with no database, such as in CI,
  relies on that folder.
* Bad, because the macros accept a fixed SQL string alone. A query whose `WHERE` clause depends on
  the user's input goes through `QueryBuilder` or `sqlx::query()`, and the compiler checks neither.
* Bad, because every call is async, so the code that calls `slicket-store` runs on an async runtime
  such as Tokio.

## Pros and Cons of the Options

### sqlx

A library that runs plain SQL, maps rows onto Rust types and checks fixed queries at compile time.

* Good, because the developer writes the SQL.
* Good, because the macros check each fixed query against the database at compile time.
* Good, because it includes a pool and migrations.
* Bad, because the compile-time check needs a database or saved query data.

### Diesel

A query builder in which the developer writes queries as Rust code, checked against a schema file
that Diesel generates.

* Good, because the compiler checks every query, dynamic ones included.
* Bad, because its queries are deeply generic Rust, and a type error in one produces a long compiler
  message.
* Bad, because it is synchronous. Async calls need the separate `diesel-async` crate.

### SeaORM

An object-relational mapper (ORM) built on sqlx, in which each entity type maps to one table.

* Good, because it writes the common queries for the developer.
* Bad, because it maps one struct to one table row, while a Slicket entity is split across several
  components.
* Bad, because the SQL it runs is hidden behind the ORM.

### tokio-postgres

An async PostgreSQL driver, and nothing more.

* Good, because it is small and exposes PostgreSQL directly.
* Bad, because the pool, the migrations and the mapping from rows to types each need another crate
  or code of Slicket's own.
* Bad, because the compiler checks no query.
